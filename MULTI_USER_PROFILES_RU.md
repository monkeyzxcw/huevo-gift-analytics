# Профили пользователей AMNYAM через huEVO

## Авторизация

Отдельной регистрации, логина и пароля AMNYAM нет. Пользователь уже авторизован в социальной сети huEVO.

Когда huEVO запускает приложение во фрейме, он передаёт query-параметры `hu_*`: `hu_app_id`, `hu_user_id`, `hu_username`, `hu_display_name`, `hu_avatar`, `hu_mode`, `hu_ts` и `hu_hash`. Фронтенд отправляет исходную строку query на `POST /api/auth/launch`.

**Подпись проверяется только на Worker.** Сервер:
1. Собирает все параметры с префиксом `hu_`, кроме `hu_hash`, включая неизвестные/будущие поля.
2. Сортирует их по имени, соединяет строками `key=value` с переводом строки.
3. Вычисляет бинарный `SHA-256(client_secret)`, затем HMAC-SHA256 и сравнивает hex-подпись за постоянное время.
4. Проверяет свежесть подписи (не более 24 часов), соответствие `hu_app_id` приложению из серверной конфигурации, режим `live|test` и числовой `hu_user_id`.
5. Создаёт или находит запись пользователя по уникальному `hu_user_id`, а затем выдаёт собственную сессию AMNYAM.

Клиентские значения из `huevo.init()` или SDK не считаются доказательством личности. В сервер отправляется оригинальный query, подписанный huEVO.

## Хранение данных

- Рыночные снимки, каталог, «База», «Ниже рынка», «Дешёвые», аналитика и детали подарков общие для всех.
- Каждому `hu_user_id` соответствует отдельная строка профиля в D1: избранное, целевые цены, уже сработавшие цели, сохранённые фильтры, звуковая настройка, оформление и сезонная тема.
- На первом подтверждённом запуске текущее локальное состояние гостя импортируется в новый профиль. При последующих запусках серверный профиль имеет приоритет.
- При переключении аккаунта в huEVO новый подписанный запуск перевязывает текущую сессию к правильному `hu_user_id`; данные предыдущего пользователя не подмешиваются.
- Имена и аватар обновляются из подписанного запуска. Аватар сохраняется только как HTTPS URL с хоста Huevo.

Серверная сессия — случайный токен; в D1 хранится только его SHA-256 хеш. Cookie имеет `HttpOnly; Secure; SameSite=None; Partitioned`, чтобы работать внутри cross-site iframe и с partitioned-cookie браузеров. Срок сессии — 30 дней. Все изменения профиля привязаны к пользователю из сессии, а не к ID, присланному клиентом.

## Настройки Worker

Для проверки запуска используются уже предусмотренные секреты Worker:
- `HU_APP_ID` (или `HUEVO_CLIENT_ID`) — ID приложения huEVO.
- `HU_SECRET` (или `HUEVO_CLIENT_SECRET`) — `client_secret`.

Значения должны быть настроены как secrets/vars Worker и не попадать в HTML, JavaScript, Git или публичный JSON. Никакие пароли пользователей AMNYAM не собираются.

## API аккаунта

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/auth/launch | Проверить подписанный запуск huEVO и создать/обновить сессию |
| GET | /api/me | Получить пользователя, подтверждённого серверной сессией |
| PUT | /api/me/profile | Сохранить профиль текущего пользователя |

Все изменения требуют same-origin запроса и действующую HttpOnly session cookie. Клиент не может выбрать чужой ID и прочитать/перезаписать его профиль.

## Развёртывание

1. В `wrangler.jsonc` используется D1 binding `DB` к базе `huevo-live-data`.
2. Миграция `migrations/0003_multi_user_profiles.sql` создаёт таблицы пользователей huEVO, серверных сессий, профилей и лимитов запуска.
3. Cloudflare deploy workflow обязательно применяет D1 миграции до публикации. Если binding или право `D1: Edit` отсутствуют, деплой останавливается.
4. Проверка `GET /api/health` должна возвращать `accounts_schema_ready: true`.

## Уведомления

Звуковая настройка синхронизируется с аккаунтом huEVO, но воспроизводится локально в открытой вкладке. Разрешение браузерных уведомлений хранится на конкретном устройстве. Это пока не Web Push: для проверки целевых цен вкладка должна оставаться открытой.
