# Huevo Gift Analytics

Панель аналитики **текущих предложений** маркета подарков Huevo: каталог, выгодные предложения, динамика медианы, история цен, поддержка автора через платежи huEVO Apps. Приложение ничего не обходит: нет прокси, смены IP, подмены заголовков и повторов после отказа.

> Важно: цена объявления и цена завершённой сделки — разные величины. Локальный сборщик отдельно читает ограниченный фрагмент подтверждённой истории Huevo. Когда по названию подарка накоплено минимум 5 сделок с известной ценой, основным ориентиром становится медиана продаж. Если сделок пока недостаточно, используется только предварительный устойчивый диапазон объявлений (минимум 5 наблюдений, подавление выбросов); при разделении цен на явно разные кластеры сигнал ниже рынка скрывается. Ушедший с рынка лот сам по себе не считается доказанной продажей.

## Источники данных и честность статуса

1. **Автоматический сбор через GitHub Actions.** Workflow запускает `scripts/collect_snapshot.py` по расписанию, используя cookies из GitHub Secrets, проверяет полный проход и обновляет публичный `cloudflare-site/data.json`. Cookies не включаются в снимок и не выводятся в логах. Для локальной диагностики можно запустить сборщик на своём компьютере.
2. **Серверный Selenium** (только если заданы `HUEVO_COOKIES_JSON` / `HUEVO_COOKIES`). Реальный HTTP-статус берётся из сетевого журнала Chrome (`status_source: network`); если журнал недоступен, блокировка определяется по тексту страницы (`inferred`), и панель так и пишет.

Полный проход — только если на странице после первой нет новых лотов. Лоты, не встреченные при полном проходе, помечаются неактивными; при неполном проходе (ошибка, блокировка, лимит страниц, подозрительно малая выборка — менее 50% прежних активных лотов) активность и снимки рынка **не меняются**.

## Публичный снимок `cloudflare-site/data.json` (схема v3)

Сборщик (`scripts/collect_snapshot.py`) пишет файл **только** после полного прохода и успешной проверки (`snapshot.validate`): нет дубликатов `lot_id`, цены — неотрицательные числа, `stats.n_total` совпадает с числом лотов. Запись атомарная (временный файл → `fsync` → замена). При блокировке, сетевой ошибке, пустом каталоге или неполном проходе (<50% прежних активных лотов) прежние лоты остаются, а в `collector` пишется статус и причина. Битый или невалидный прежний файл никогда не «чинится» пустым снимком.

Поля v3 (схема автоматически мигрирует старые v1/v2 снимки): `lots` (с `first_seen`, `last_seen`, `history` изменения цены, `gift_details` и `gift_instance`), `gone_lots` (с причиной исчезновения и результатом проверки истории), `catalog_events` (новые события истории экземпляров и предполагаемое снятие с маркета), `snapshots`, `price_bins`, `categories`, `top_expensive`, `changes`, `deals`, `drops`, `sales`. Повторный сбор без изменений в течение 10 минут не добавляет дубль точки истории.

«Не найден» ≠ «продан»: лот мог быть продан, снят или скрыт. История сделок собирается отдельно локальным `scripts/collect_history.py --local-profile --pages 3`; по умолчанию расписание читает только первые 3 страницы за один запуск, а не сканирует весь архив. Локальная `history.db` не публикуется. Флаг `--with-sales` публикует только агрегаты, если накоплено не менее 20 записей с известной ценой: общая статистика и профили по названию подарка (count, median, P25/P75, min/max). Имена продавцов/покупателей и отдельные строки сделок в публичный снимок не попадают.

Поле `sold_at` заполняется только при наличии явной календарной даты/времени с часовым поясом или Unix timestamp в HTML. Если Huevo показывает лишь часы и минуты, календарная дата остаётся неизвестной: график продаж по датам не строится, а вместо него показываются медиана и диапазон без выдуманной хронологии.

После успешного полного каталожного прохода сборщик выборочно открывает до 8 новых/просроченных страниц /market/lot/<id> за запуск (HUEVO_DETAIL_LIMIT). Кэш характеристик — до 60 дней; между запросами минимум 3 секунды. Из карточки лота извлекаются разрешённые атрибуты и ссылка на конкретный экземпляр /gift/<gift_id>; market lot ID и gift ID — разные идентификаторы.

Отдельная очередь открывает не более 8 уникальных страниц экземпляров за запуск (HUEVO_INSTANCE_LIMIT). Дубликаты одного gift ID объединяются, исчезнувшие с рынка лоты идут первыми. История и характеристики кэшируются; уже известная история планово перепроверяется не чаще чем через 30 дней, а отсутствие распознанного блока истории — через 2 дня. Когда лот исчезает после полного прохода, проверка его экземпляра запускается принудительно, даже если кэш ещё свежий. Между страницами выдерживается минимум 3 секунды; блокировка Huevo немедленно останавливает очередь и включает общий cooldown.

Со страницы /gift/<id> сохраняются номер экземпляра, тираж, редкость, цена выпуска/дропа, отметка о распроданном тираже, автор, коллекция, текущий публичный handle владельца и публичные события истории (тип, from/to handles, отображаемое время). История экземпляра дополняется append-only: ранее собранные события не удаляются. Относительные подписи времени («вчера», «сегодня») не используются как идентификатор события, а точная дата не выдумывается. События истории не содержат цену сделки: цена в объявлении, цена дропа и цена продажи остаются разными величинами.

Если исчезнувший лот имеет ранее собранную историю и после исчезновения в ней нет новой продажи или передачи, он помечается «Вероятно снят продавцом». Новая запись «Продан в Маркете» даёт статус продажи; «Передан» — статус передачи. Если история ранее не была собрана, фиксируется базовая история и AMNYAM ждёт следующей проверки; если страница не показывает историю или недоступна — остаётся «Ожидает проверки». Исчезновение не называется подтверждённой продажей без соответствующего события. Эти статусы и события доступны во вкладке «Изменения каталога» → «Не найдены» / «История экземпляров».

Детали продавца не копируются из произвольных элементов страницы. В историю попадают только публичные handles, непосредственно указанные в блоке истории самого подарка. При блокировке Huevo дополнительный проход немедленно прекращается; ошибка enrichment не отменяет уже успешно собранный полный рыночный проход.

История цены каждого объявления хранится до 30 дней (настраивается `HUEVO_RETENTION_HOURS`, максимум 720 часов). Это история цены конкретного предложения, а не статистика завершённых сделок.

Звуковые сигналы целевой цены генерируются браузером и выключены по умолчанию. Их можно отдельно включить в разделе «Избранное»; для срабатывания страница должна быть открыта и получать обновления. Это локальный звук, не серверное push-уведомление.

Временные сетевые сбои (таймаут/обрыв соединения) повторяются не более 2 раз с нарастающей паузой; 403/418/429, страница входа, 5xx, DNS/TLS повторов не получают, а блокировка включает паузу (не меньше `Retry-After`).

## Что делать при 418 / 403 / 429 / сетевых ошибках

| Симптом | Значение | Действие |
|---|---|---|
| 403 / 418 / 429 | Huevo ограничил доступ (реальный статус из сети или признак на странице) | Сбор остановлен; пауза не короче `CRAWL_BLOCK_COOLDOWN_HOURS` и не короче `Retry-After`. Пауза хранится в БД и переживает перезапуск. Подождите; используйте браузерный сбор из своей авторизованной вкладки |
| страница входа | сессия или домен cookies не подходят | перелогиньтесь в браузере и используйте браузерный сбор |
| 5xx | временная проблема источника | повторить позже |
| `dns` / `tls` / `timeout` / `connect` | сеть узла или источник недоступен | проверить «Проверку доступа к Huevo» во вкладке «Сборщик» |
| нет карточек | изменилась разметка или не отрисовался JS | сверить селекторы в `lot_parser.py`, обновить фикстуры |

Проверка доступа: вкладка «Сборщик» → «Проверить доступ к Huevo» (один запрос к `/` и `/market/gifts?page=1`, не чаще раза в `DIAG_COOLDOWN_SECONDS`, без cookies и тела страницы в ответе).

## Запуск целиком в Docker Compose (VPS / свой сервер)

В репозитории есть `Dockerfile` и `docker-compose.yml`: контейнер запускает веб-панель, API и планировщик серверного сбора. SQLite хранится в именованном Docker volume `huevo-gift-analytics-data`, поэтому данные переживают пересоздание/перезапуск контейнера.

1. Установите Docker Engine с Compose plugin на сервере и склонируйте репозиторий.
2. Создайте конфигурацию: `cp .env.example .env`.
3. В `.env` замените `INGEST_TOKEN` на длинный случайный секрет. Для автоматического серверного сбора задайте `HUEVO_COOKIES_JSON` как JSON-массив cookies **одной строкой**. Не коммитьте `.env` и не отправляйте cookies в чат.
4. Запустите: `docker compose up -d --build`.
5. Проверьте: `docker compose ps`, `docker compose logs -f huevo-gift-analytics`, затем откройте `http://IP-СЕРВЕРА:8000`. Для публичного доступа настройте HTTPS через домен и reverse proxy; не выставляйте административные секреты в URL.
6. Обновление: `git pull && docker compose up -d --build`.

Важное про сессию: Docker сохраняет конфигурацию из `.env` и базу между перезапусками, но **не может заставить Huevo сохранять действительность сессии**. Если Huevo отзовёт/просрочит cookies или потребует повторный вход, потребуется обновить `HUEVO_COOKIES_JSON` в `.env` и пересоздать контейнер командой `docker compose up -d`. Если cookies не заданы, панель запустится, но автоматический серверный сбор не начнётся. Не используйте `docker compose down -v`: флаг `-v` удалит постоянную базу.

Для локального теста на компьютере команды те же; панель будет доступна по `http://localhost:8000`.

## Публикация на Cloudflare

Рабочий сайт: **https://huevo-gift-analytics.monkeyzxc1437.workers.dev**.

Cloudflare Worker обслуживает интерфейс из `cloudflare-site/` и API из `src/worker.js`. Вкладки рынка общие для всех пользователей; отдельные аккаунты и персональные настройки хранятся в Cloudflare D1 (`DB`). Python/Selenium и авторизованный вход в Huevo в браузере пользователей Cloudflare не запускает. Имя Worker — `huevo-gift-analytics`.

Сбор идёт на твоём Windows-ПК:
1. Один раз запусти `run_local_collector.bat`: откроется отдельный локальный Chrome-профиль, в котором нужно войти на Huevo. Сессия хранится только на этом компьютере.
2. Для автоматического запуска раз в 6 часов запусти `install_auto_schedule.bat`. Планировщик Windows работает, пока пользователь вошёл в систему, а ПК включён.
3. Сборщик обновляет `cloudflare-site/data.json` и отправляет commit в GitHub. Workflow `.github/workflows/cloudflare-static.yml` проверяет JSON и публикует статический сайт в Cloudflare.

Для деплоя нужны только GitHub Secrets `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`. **Cookies Huevo не добавляй в GitHub Secrets**: версия v6 использует локальный профиль Chrome. Настройка описана в `CLOUDFLARE_FREE_SETUP_RU.md`.

Если каталог не удалось собрать полностью или Huevo ограничил доступ, последний корректный снимок остаётся без изменений. Блокировки не обходятся.

## Пользовательские аккаунты

Приложение поддерживает гостевой режим и регистрацию нескольких пользователей. Пользователь автоматически определяется по подписанному `hu_user_id` при запуске приложения из huEVO; отдельные логин и пароль не нужны. У каждого аккаунта собственные избранное, целевые цены, сохранённые фильтры, звук и оформление; общие вкладки и аналитика рынка остаются одинаковыми для всех. Данные профиля хранятся в D1 и не публикуются вместе с `data.json`. При первом запуске из huEVO локальные настройки гостя переносятся в новый профиль. Подробности, API и модель безопасности: [`MULTI_USER_PROFILES_RU.md`](MULTI_USER_PROFILES_RU.md).

Подпись `hu_*` проверяется на Worker через HMAC-SHA256 и секрет приложения; SDK/фронтенд не используется как подтверждение личности. Подробнее: [`MULTI_USER_PROFILES_RU.md`](MULTI_USER_PROFILES_RU.md).

## Переменные окружения

`INGEST_TOKEN`, `HUEVO_BASE_URL`, `HUEVO_COOKIES_JSON` / `HUEVO_COOKIES`, `HUEVO_DB`, `CRAWL_DELAY`, `MAX_PAGES`, `CRAWL_BLOCK_COOLDOWN_HOURS`, `AUTO_REFRESH_HOURS`, `DIAG_COOLDOWN_SECONDS`, `LOG_LEVEL`, `HUEVO_CLIENT_ID`, `HUEVO_CLIENT_SECRET` относятся к дополнительному локальному FastAPI/Docker-режиму. **Для Cloudflare Worker они не нужны**. Для публикации нужны `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` в GitHub Secrets. Токен должен иметь право `D1: Edit`: deploy workflow применяет миграции и остановится, если аккаунтные таблицы не удалось создать.

## API

Cloudflare Worker: `POST /api/auth/launch`, `GET /api/me`, `PUT /api/me/profile` — авторизация подписанного запуска huEVO и личные настройки (для закрытых операций требуется cookie текущей сессии). Рынок остаётся общим.

Публичные (GET): `/health`, `/api/status`, `/api/diagnostics`, `/api/catalog` (`q, sort, status, rarity, min_price, max_price, limit≤200, offset`), `/api/facets`, `/api/lots/by-ids`, `/api/lots` (совместимость), `/api/stats`, `/api/highlights`, `/api/deals`, `/api/drops`, `/api/analytics/summary`, `/api/analytics/snapshots`, `/api/analytics/price-history`, `/api/history/{lot_id}`, `/api/support/config|stats|status/{id}`.

Защищены `Authorization: Bearer <INGEST_TOKEN>` (токен в query-строке не принимается; 10 неверных попыток за 5 минут → 429): `POST /api/ingest`, `POST /api/ingest/complete`, `POST /api/crawl`, `POST /api/diagnose-huevo`, `GET /api/backup`.

Платежи: `POST /api/support/intent` (подпись запуска `hu_*`), `POST /api/support/callback` (подпись `X-Huevo-Signature` по сырому телу). Финальный статус платежа не перезаписывается; повторные callback безопасны.

## Безопасность

Размеры запросов ограничены (ingest — 2 МБ и 1000 лотов), `lot_id` — только цифры, SQL — параметризованный, `LIKE` экранируется, сортировка — из белого списка, весь пользовательский текст в интерфейсе экранируется, CSP запрещает inline-скрипты и стили, CSV нейтрализует формулы, CORS только для хостов Huevo, внешние ссылки — `rel="noopener noreferrer"`.

## Ограничения

- Разметка парсера (`.mk-gcard`, `.mk-gtitle`, `.mk-price`…) выведена из прежних наблюдений и фикстур; на живом Huevo из этой среды не проверялась.
- «Последний лот» — лот, замеченный сборщиком последним; время выставления сайт не отдаёт.
- Оплата работает только внутри huEVO (нужны подписанные параметры запуска); в боевом режиме не проверена.
- История и аналитика копятся по мере проходов; пока снимков меньше двух, панель пишет «Недостаточно данных».
